## Summary

A skill is a local directory containing a `SKILL.md` (YAML frontmatter with `name` and `description`, then Markdown instructions) and optional text files. An application loads a catalog from explicit roots. It chooses which skills an agent run may use (`include`) and which are active from the start (`activate`). It may also let the model load permitted skills itself (`allowModelSelection`).

Applying a skill adds a system-prompt section and read-only tools for that one run. It never creates tools, changes permissions or bypasses hooks. Without a skill binding, every request is exactly as before.

### Parsing

- Accepted fields: exactly `name` and `description`.
- YAML rules: duplicate keys, unknown tags, anchors and aliases are rejected; the core schema is used with no custom tags.
- The file must be strict UTF-8 without NUL bytes.
- `name` must match `[a-z0-9]+(?:-[a-z0-9]+)*` and be at most 64 characters.
- `description` must be nonempty and at most 1,024 characters.
- The body after the frontmatter must be nonempty.

### File access

- **`readBounded`** reads only regular files:
  - The file is opened with `O_NOFOLLOW` and checked with `fstat`.
  - Files over the limit are refused before any content is read.
  - An optional `reserve(size)` callback runs synchronously before the read, so budgets cannot be oversubscribed by parallel reads.
  - At most `max + 1` bytes are read, so a file that grew since the check is detected.
- **`resolveResource`** rejects:
  - absolute paths (POSIX, Windows and drive letters);
  - empty, `.` and `..` segments;
  - symbolic links at any level;
  - anything that is not a regular file at the end.

### Catalog

**`loadSkillCatalog({ roots, baseDir, limits?, signal? })`**:
- Resolves relative roots against the required `baseDir`, and scans only those roots, one level deep, in sorted order.
- A child directory without `SKILL.md` is skipped. A symbolic link to a directory is reported, not followed.
- The name must equal the directory name. A name found in two roots is a diagnostic and neither copy is used.
- The document size limit and `maxCatalogEntries` are enforced.
- Problems become `catalog.diagnostics` (path, field, message) rather than exceptions. `list()` returns the valid skills, and `prepare()` throws `SkillCatalogError` while any diagnostic exists.

**Other functions:**
- `load` re-reads the document and rejects with `SkillChangedError` if its digest differs from the catalog's.
- `verify(manifest)` re-checks the documents and resources a manifest lists, and names each difference.
- `skillManifest(usage)` produces a version-1 JSON manifest.

### Preparation

`catalog.prepare(selection, { signal, onEvent })` builds the context and tools for one agent run.

**Selection:**
- `include` and `activate` are deduplicated and sorted.
- Unknown names and activation outside `include` fail before any model call. An empty `include` permits nothing.

**Context:** one "# Skills" section. It states that skills cannot grant tools, permissions or approvals, and contains:
- the activated skill bodies, each wrapped with its name and `sha256` digest, plus how to read resources;
- with model selection, the names and descriptions of the other permitted skills.

A section over `maxContextBytes` is rejected, never truncated.

**Tools:**
- **`skills_load`** is offered only with model selection. It loads only permitted skills and activates the loaded skill for the rest of the run.
- **`skills_read`** reads files of active skills only.
- Both are annotated read-only and idempotent.
- The read budget is kept per run, and repeated reads count against it.
- A file whose content changes between two reads in the same run is rejected.
- Failed reads do not consume budget.
- Errors are thrown and become ordinary tool error results, so the model can correct a name or path.

**Usage and events:**
- `usage()` returns deeply frozen snapshots.
- `onEvent` reports preparation, loads and reads with names, digests, paths, sizes and outcomes, but never document bodies. A throwing callback is ignored.

### Agent adapter

`withSkills(agent, runOptions, binding)`:
- Rejects agent or extra tools that use the reserved names `skills_load` and `skills_read`.
- Prepares the binding with the run's signal.
- Appends the skill context after the caller's `context` (ADRs) and the tools after `extraTools`.
- Returns the options object unchanged when there is no binding.

The `Agent` class has no new fields.

### Configuration

`skillsFromConfig(config, { baseDir?, activate?, signal?, onEvent? })` loads the config's `skills` section as a binding:
- Roots resolve against `configDir`. Relative roots without a directory are an error.
- `activate` replaces the configured activation.
- It returns `undefined` when there is no `skills` section.

### Integrations

- [`src/agents/workflow.ts`](../../src/agents/workflow.ts):
  - `WorkflowOptions.skills` applies a binding to every step. `StepOptions.skills` replaces it for one step, and `false` removes it; selections are never merged.
  - Each step gets a fresh preparation, and `WorkflowStepResult.skills` holds its manifest.
  - Without a binding the code path is unchanged; `test/workflow-compat.test.ts` passes unedited.
- [`src/graph/agent-node.ts`](../../src/graph/agent-node.ts):
  - `AgentNodeOptions.skills` is set per node and prepared on every attempt.
  - Skill events are emitted as `custom` node events named `"skill"`, so the executor does not depend on skills.
  - The output gains `skills`, the manifest of what the node used.
- [`src/cli/chat.ts`](../../src/cli/chat.ts): `ChatTurnOptions.skills` is prepared on every turn. Skill text loaded in earlier turns stays in the transcript, but activation does not carry over.

## CLI

- [`src/cli/args.ts`](../../src/cli/args.ts):
  - New commands: `umio skills [list]` and `umio skills show <name>`.
  - New global options: `--skill <name>` (repeatable) and `--no-skills`. Using both is a usage error.
- [`src/cli/skills.ts`](../../src/cli/skills.ts) (new): `cliSkills` builds the binding for `ask` and chat.
  - `--skill` replaces `activate` but may only name skills in `include` (exit 2 otherwise, with the permitted list).
  - `--skill` without a `skills` section is a usage error.
  - Catalog diagnostics stop the run, with a hint to use `--no-skills`.
- [`src/cli/app.ts`](../../src/cli/app.ts):
  - `umio skills` lists permitted skills with activation and short digests. It exits 1 on diagnostics or a permitted skill that was not found; `--json` gives the full structure.
  - `umio skills show` prints a permitted skill with its full digest. Non-permitted skills are refused and never printed.
  - `ask` passes the binding to the chat turn.
- [`src/cli/repl.ts`](../../src/cli/repl.ts):
  - The catalog is loaded once per session and prepared again every turn.
  - The banner lists active skills.
- [`src/cli/help.ts`](../../src/cli/help.ts): new `skills` topic, new options in the main help, and an updated `ask` usage line.
- The skill tools are read-only, so the existing confirmation flow auto-approves them. `--tools` still controls ordinary tools only.

### Catalog, selection and resource tests

- **Catalog:** deterministic listing and one-level discovery.
- **Diagnostics:**
  - missing frontmatter and malformed YAML;
  - duplicate keys and unknown fields;
  - invalid names and a name/directory mismatch;
  - an empty body, and a missing or too-long description;
  - aliases, custom tags and binary content;
  - duplicate names across roots and a missing root.
- **Limits and changes:**
  - the document size and entry limits, and a symlinked skill directory;
  - rejection of a `SKILL.md` changed after loading.
- **Selection:**
  - activation order and deduplication, and the prompt wording;
  - empty `include`, unknown names, activation outside `include`, and malformed input;
  - summaries without bodies when the model selects;
  - a resource read before activation, and unauthorized loads;
  - frozen usage snapshots and per-preparation isolation;
  - the context limit and cancellation.
- **Resources:**
  - relative and backslash paths;
  - traversal, absolute and drive paths, file and directory symlinks, directories, binary files and empty paths;
  - per-file and per-run limits, including repeats and failed reads that cost nothing;
  - parallel reads that cannot oversubscribe the budget;
  - a file changed between reads;
  - event contents without bodies, and a throwing callback.

### Integration tests

- **Prompt order:** caller context, then skills, then role, then standing instructions.
- **Isolation:** unchanged options without a binding, and rejection of reserved tool names.
- **Model selection:** a multi-step scripted run in which the model reads before loading (error), loads an unpermitted skill (error), loads, then reads. Hooks see all four calls, and the system prompt stays constant.
- **Delegation:** a delegated agent receives no parent skills.
- **Workflow:** default, replaced and disabled bindings, with a manifest per step.
- **Graph node:** node events and the output manifest.
- **Manifests:** verification passes on unchanged content and fails naming the changed file.
- **Config:** schema validation (`include` required, `activate` within `include`, names, limits, strictness), and `skillsFromConfig` root resolution and activation replacement.
- **Chat:** turns re-prepare, so activation does not carry over.

### CLI tests

- **`skills list` and `show`:** activation marks, JSON output, and a non-permitted skill that stays hidden.
- **Errors:** diagnostics and missing permitted skills exit 1; no `skills` section is not an error.
- **`ask`:** configured activation, replacement by `--skill`, multiple `--skill` flags, and `--no-skills`.
- **Flags:** `--skill` outside `include` or without a `skills` section exits 2, as does `--skill` with `--no-skills`.
- **Confirmation:** with model selection, a non-interactive `ask` without `--yes` loads and reads skills without confirmation.

## Not implemented

- **Phase 4 durable enforcement.** Graph checkpoints do not record skill manifests on failed attempts, and `resume()` or retries do not verify skill content automatically. A completed agent node's output does contain the manifest, and `catalog.verify(manifest)` can check it. Applications must pin skill packages and bump the graph `version` when they change. This matches the design's stated first-release behavior.
- **Deferred by the design (§12):** compatibility with external `SKILL.md` formats, extra metadata fields, remote packages, automatic relevance ranking, binary assets, and a script runner.
- **Chat commands:** there is no `/skills` slash command. Chat uses the configured activation or the `--skill` and `--no-skills` flags given at start.

## Remaining limitations

- Path checks assume the skill roots are application-controlled. They are not a sandbox against another process changing files during a read. The design states this.
- Byte limits bound I/O and prompt size, not model tokens.
- With model selection, a dependent `skills_read` in the same parallel batch as its `skills_load` returns an error the model must retry, as the design describes.
